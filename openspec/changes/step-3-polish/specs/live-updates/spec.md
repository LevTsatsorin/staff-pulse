## Purpose

Доставка изменений орг-структуры в клиент в реальном времени с применением патчей к уже загруженной модели без полного рефетча и с устойчивым восстановлением соединения.

## ADDED Requirements

### Requirement: Контракт сообщений
Сервер ДОЛЖЕН при подключении отправлять `{ "type": "hello", "version": number }`, а при изменениях — `{ "type": "patch", "version": number, "changes": [{ "id": string, "fields": { "headcount"?: number, "budget"?: number, "performance"?: number }, "updatedAt": string }] }`. Версии монотонно растут на 1 с каждым патчем. Клиент ДОЛЖЕН валидировать каждое сообщение схемой и игнорировать невалидные.

#### Scenario: Приветствие
- **WHEN** клиент установил соединение
- **THEN** первым сообщением приходит `hello` с текущей версией данных

#### Scenario: Невалидное сообщение
- **WHEN** пришло сообщение, не соответствующее схеме
- **THEN** оно игнорируется, соединение не разрывается, состояние модели не меняется

### Requirement: Применение патча без рефетча
Патч с версией `model.version + 1` ДОЛЖЕН применяться к кэшированной модели напрямую: изменяются только указанные узлы, агрегаты пересчитываются только для этих узлов и их предков, ссылки на остальные узлы сохраняются. Сетевой запрос при этом не выполняется.

#### Scenario: Один узел
- **WHEN** пришёл патч, меняющий headcount команды
- **THEN** строка команды, её отдела и дивизиона показывают новые агрегаты, остальные строки не перерисованы, запросов к `/api/org-tree` нет

#### Scenario: Пачка изменений
- **WHEN** в одном патче несколько узлов
- **THEN** все изменения применены атомарно одним обновлением кэша

#### Scenario: Эквивалентность полному пересчёту
- **WHEN** к модели последовательно применено 1000 случайных патчей
- **THEN** агрегаты совпадают с построенными заново из итоговых узлов (unit-тест)

### Requirement: Сверка версий
Патч с версией не больше текущей ДОЛЖЕН игнорироваться; патч с пропуском версии или с неизвестным `id` ДОЛЖЕН приводить к одному фоновому рефетчу снапшота. Если `hello.version` больше версии модели, выполняется рефетч.

#### Scenario: Пропущенная версия
- **WHEN** модель на версии 10, пришёл патч версии 12
- **THEN** патч не применяется, выполняется один рефетч, после него версия ≥ 12

#### Scenario: Повтор старой версии
- **WHEN** пришёл патч версии 9 при модели на версии 10
- **THEN** ничего не происходит

### Requirement: Восстановление соединения
При обрыве клиент ДОЛЖЕН переподключаться с экспоненциальной задержкой и jitter (база 1 с, потолок 30 с), сбрасывать счётчик попыток при успешном подключении и переподключаться немедленно по событию `online`. После восстановления выполняется один рефетч снапшота.

#### Scenario: Сервер остановлен
- **WHEN** соединение оборвано и сервер недоступен
- **THEN** попытки идут с растущими интервалами примерно 1, 2, 4, 8… с (с jitter), не превышая 30 с

#### Scenario: Сервер вернулся
- **WHEN** очередная попытка успешна
- **THEN** индикатор переходит в «live», выполняется рефетч, счётчик попыток сброшен

#### Scenario: Двойной монтаж в StrictMode
- **WHEN** приложение запущено в dev с StrictMode
- **THEN** открыто ровно одно соединение, каждый патч применяется один раз

### Requirement: Индикатор соединения
Шапка ДОЛЖНА показывать состояние соединения текстом и цветом: «подключение», «live», «переподключение через N с», «офлайн».

#### Scenario: Обратный отсчёт
- **WHEN** запланирована попытка через 8 с
- **THEN** индикатор показывает «переподключение через 8 с» и отсчитывает до 0

### Requirement: Подсветка обновлённых ячеек
Ячейки, значение которых изменилось из-за патча (включая агрегаты предков), ДОЛЖНЫ подсвечиваться с плавным затуханием около 1.5 с; при первичной загрузке подсветки нет; при `prefers-reduced-motion` подсветка без анимации.

#### Scenario: Патч по команде
- **WHEN** патч изменил бюджет команды
- **THEN** ячейки бюджета команды, отдела и дивизиона подсвечены и гаснут за ~1.5 с, остальные ячейки без подсветки

#### Scenario: Первичная загрузка
- **WHEN** данные загружены впервые
- **THEN** ни одна ячейка не подсвечена

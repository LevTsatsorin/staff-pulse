## Purpose

Клиентский слой данных: получение снапшота орг-структуры, валидация контракта, кэширование, отмена и нормализация в модель, от которой рендерятся дерево и таблица.

## ADDED Requirements

### Requirement: Валидация ответа API
Клиент ДОЛЖЕН проверять ответ `GET /api/org-tree` по схеме; невалидный ответ ДОЛЖЕН приводить к состоянию ошибки с понятным сообщением, а не к падению рендера.

#### Scenario: Невалидный ответ
- **WHEN** сервер вернул узел без `id` или с `performance` вне диапазона 0–100
- **THEN** UI показывает состояние ошибки «Сервер вернул данные в неожиданном формате» и кнопку «Повторить»

#### Scenario: Нарушена целостность дерева
- **WHEN** в ответе дублируется `id`, есть узел с несуществующим `parentId` или цикл по `parentId`
- **THEN** UI показывает состояние ошибки данных с указанием причины

### Requirement: Кэширование запроса
Данные ДОЛЖНЫ запрашиваться через слой кэширования со stale time 5 секунд: повторное использование в пределах 5 с не создаёт сетевого запроса; по истечении — фоновая ревалидация с сохранением текущих данных на экране.

#### Scenario: Повторный монтаж в пределах stale time
- **WHEN** потребитель данных размонтирован и смонтирован снова в течение 5 с
- **THEN** новый сетевой запрос не выполняется

#### Scenario: Ревалидация после stale time
- **WHEN** прошло более 5 с и потребитель снова монтируется или окно получает фокус
- **THEN** выполняется фоновый запрос, старые данные остаются на экране до его завершения, в шапке виден тихий индикатор обновления

#### Scenario: Данные не изменились
- **WHEN** фоновая ревалидация вернула эквивалентные данные
- **THEN** ссылки на модель сохраняются, потребители не перерисовываются

### Requirement: Отмена запроса
Незавершённый запрос ДОЛЖЕН отменяться при размонтировании последнего потребителя; отмена не считается ошибкой.

#### Scenario: Размонтирование во время загрузки
- **WHEN** потребитель размонтирован до ответа сервера
- **THEN** запрос прерван через AbortSignal, состояние ошибки не показывается

### Requirement: Нормализованная модель
После валидации данные ДОЛЖНЫ нормализоваться один раз в модель: узлы по id, списки детей в исходном порядке, корни (допустим лес), глубина каждого узла, версия снапшота из `ETag`.

#### Scenario: Несколько корней
- **WHEN** в ответе несколько узлов с `parentId: null`
- **THEN** все они становятся корнями, порядок исходного массива сохраняется

#### Scenario: Глубина узлов
- **WHEN** узел является ребёнком ребёнка корня
- **THEN** его глубина равна 2, а у корня — 0

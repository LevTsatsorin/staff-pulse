# Модель данных

## Контракт API

`GET /api/org-tree` отдаёт плоский массив узлов. Схема — `shared/orgTree.ts` (zod), общая для клиента и сервера.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | string | непустая, уникальная |
| `name` | string | непустая |
| `parentId` | string \| null | `null` у корня; ссылается на существующий `id` |
| `headcount` | int | ≥ 0, собственная численность узла |
| `budget` | number | ≥ 0, собственный бюджет узла |
| `performance` | number | 0–100 |
| `updatedAt` | string | ISO 8601 |

Ответ сопровождается `ETag` (версия данных) и `Cache-Control: no-cache`.

## Нормализованная модель

После валидации массив один раз превращается в `OrgModel` (`src/types/orgModel.ts`):

```ts
type OrgModel = {
  nodes: Record<string, OrgNode>;          // узел + depth
  childrenIds: Record<string, string[]>;   // порядок детей как в ответе
  rootIds: string[];                        // корней может быть несколько
  aggregates: Record<string, Aggregate>;
  version: number;                          // из ETag
  snapshotVersion: number;                  // версия на момент загрузки снапшота
};
```

Хранятся plain-объекты, а не `Map`: `structuralSharing` TanStack Query сравнивает только массивы и plain-объекты.

Проверки целостности при построении (`buildOrgModel`): повтор `id`, ссылка на несуществующего родителя, цикл по `parentId`. Любое нарушение — `OrgDataError`, UI показывает состояние ошибки.

Глубина считается подъёмом к первому предку с уже известной глубиной, поэтому порядок узлов в ответе не важен, а общий обход линейный.

## Агрегация

Для каждого узла `v` с детьми `c₁…cₖ`:

```
totalHeadcount(v)  = headcount(v) + Σ totalHeadcount(cᵢ)
totalBudget(v)     = budget(v)    + Σ totalBudget(cᵢ)
perfWeightedSum(v) = performance(v) · headcount(v) + Σ perfWeightedSum(cᵢ)
avgPerformance(v)  = perfWeightedSum(v) / totalHeadcount(v),  или null при totalHeadcount(v) = 0
```

Средняя эффективность взвешена по численности: команда из 15 человек влияет на среднее отдела втрое сильнее команды из 5.

`perfWeightedSum` хранится отдельно от среднего. Благодаря этому агрегат любого узла собирается из **агрегатов прямых детей** без повторного обхода поддерева (`aggregateNode`). Это основа инкрементального пересчёта на этапе live-обновлений: изменение узла пересобирает только его и цепочку предков.

Пересборка из детей, а не дельта (`total += new − old`), выбрана намеренно: дельты на числах с плавающей точкой накапливают погрешность.

Сложность: построение модели и агрегатов O(n), один раз после загрузки, внутри `queryFn`. Компоненты и таблица читают готовые значения. См. [ADR-002](adr/002-aggregates-in-cache.md).

`avgPerformance = null` отображается как «—» и при сортировке всегда идёт последним.

## Строки таблицы

Таблица строится цепочкой чистых функций, каждая в своём `useMemo`:

```
OrgModel ──toTableRows──▶ все строки ──filterRows(query)──▶ ──sortRows(sort)──▶ отображаемые строки
```

- `toTableRows` обходит дерево в прямом порядке (pre-order), поэтому без сортировки таблица повторяет дерево. Строка содержит путь родителей («Коммерция · Продажи»), уровень и агрегаты, взятые из модели. Индекс обхода `order` используется как стабильный вторичный ключ сортировки.
- `filterRows` сравнивает название без учёта регистра (`ru-RU`). Агрегаты от фильтра не зависят.
- `sortRows` сортирует копию: строки через `Intl.Collator('ru-RU')`, числа численно, `null` в конце, при равенстве — порядок дерева.

Смена фильтра или сортировки не трогает `toTableRows` и тем более агрегацию.

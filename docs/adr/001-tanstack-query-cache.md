# ADR-001. TanStack Query как слой кэширования

## Контекст

ТЗ требует запрос через слой кэширования со stale time 5 секунд, отмену запросов при размонтировании, stale-while-revalidate «или аналог» и инвалидацию кэша только при реальном изменении данных. На этапе 03 в кэш придётся применять патчи без полного рефетча.

## Решение

Использовать TanStack Query v5 с одним `QueryClient` (`staleTime: 5_000`, `retry: 1`). `queryFn` получает `AbortSignal` и пробрасывает его в `fetch`. В кэше хранится не сырой ответ, а нормализованная модель, построенная внутри `queryFn`. Патчи (этап 03) применяются через `setQueryData`.

## Альтернативы

- **Собственный кэш** (`Map` + `useEffect` + `AbortController`). Даёт полный контроль, но это 100+ строк с гонками, дедупликацией и таймерами, которые нужно тестировать; для тестового задания за 2–3 дня — риск без выигрыша. ТЗ прямо допускает «аналог».
- **SWR.** Нет `staleTime` в нужной семантике (только `dedupingInterval`) и нет передачи `AbortSignal` в fetcher, то есть отмена при размонтировании не закрывается из коробки.

## Последствия

- «Stale time», отмена и дедупликация — конфигурация, а не код; меньше поверхности для ошибок.
- `structuralSharing` работает только с plain-объектами и массивами, поэтому модель хранится в `Record<string, …>`, а не в `Map`.
- Добавляется зависимость ~12 КБ gzip; бюджет 200 КБ не под угрозой.
- Собственный код — это модель, агрегация и патчи (`utils/tree/*`), покрытые unit-тестами; библиотека отвечает только за транспортный жизненный цикл.
